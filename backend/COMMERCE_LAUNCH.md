# Milterra commerce activation

Production auth is fail-closed. Set `APP_ENV=production`, `ALLOW_DEMO_LOGIN=false`, a unique `JWT_SECRET`, HTTPS `STOREFRONT_BASE_URL`, encrypted `REDIS_URL`, working SMTP credentials for password recovery, and MSG91 `SMS_API_KEY` plus an approved `SMS_TEMPLATE_ID` whose `VAR1` is the six-digit login code. Admin and seller OTP login sends through MSG91; a failed submission returns 503 rather than claiming a code was sent. Requests are rate limited across workers with Redis. Demo credentials and fixed codes work only when both a local development/test environment and `ALLOW_DEMO_LOGIN=true` are set; the Flutter demo UI additionally requires a debug build with `--dart-define=ENABLE_DEMO_UI=true`. Rotate or remove any accounts that previously used the published demo password before rollout.

New checkouts default to commercial orders (`PRELAUNCH_MODE=false`). Existing purchase interests keep their `is_prelaunch_interest` flag and do not become paid orders automatically. Before starting production, apply all Alembic migrations, configure delivery coverage, and set `PRELAUNCH_MODE=false` explicitly in the backend environment. Set it to `true` only to resume interest-only checkout.

Apply migration `auth_otp_limits_v18` as well as the commerce migrations before running the new backend. Use `INIT_DB_ON_STARTUP=false` in production. Build Flutter web with `--dart-define=API_BASE_URL=https://<your-api-host>`; without this the app falls back to a localhost HTTP API. Serve the site and API over HTTPS, use the root or backend Dockerfile without `--reload`, and keep PostgreSQL, Redis, and product-media storage private and backed up. `docker-compose.yml` is a development setup with example database credentials, not a production manifest.

For online checkout, configure `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, and `RAZORPAY_WEBHOOK_SECRET`. Register an HTTPS Razorpay webhook at `/api/v1/marketplace/orders/webhooks/razorpay` for `payment_link.paid`, using the same webhook secret. The server creates a standard hosted payment link for each online order. An order becomes paid only after the server fetches the link and confirms the full amount, currency, and stored reference. The customer can retry payment and check its status on the order page. If keys are absent, checkout shows COD only, and the backend rejects online checkout before reserving stock. Production startup requires all three Razorpay settings in live mode.

Each payment link expires after `COMMERCE_PAYMENT_LINK_EXPIRY_MINUTES` (default 30). Customers can request another link for the same pending order. The backend checks and closes unpaid online orders after `COMMERCE_UNPAID_ORDER_TTL_HOURS` (default 24), cancelling any still-active link before restoring stock. A paid order cancellation records a request for staff review; fulfillment and courier booking pause while the request is open. Its payment and inventory stay unchanged until a processed provider refund is verified. If staff rejects the request, fulfillment can resume. COD orders can be cancelled before packing without a refund.

COD orders are confirmed with payment pending. They may be packed and booked with a COD-capable courier. Delivery tracking does not prove that the courier remitted the cash, so an admin records a real remittance reference after delivery. This marks payment paid. A manually dispatched order must carry a real courier name and AWB.

For manual delivery coverage, mark the destination pincode serviceable and set its delivery fee in the admin data. Automatic Delhivery booking additionally requires `SHIPPING_AUTO_BOOK_ENABLED=true`, the courier credentials and pickup location, and valid product/package weights and dimensions. The configured origin pincode is `201305`; change `SHIPPING_ORIGIN_PINCODE` if dispatch moves. Courier booking is only eligible after payment confirmation or COD order confirmation and packing.

For a Razorpay-paid order, staff must process any refund in Razorpay and enter the `rfnd_...` reference in the Milterra refund/return action. The backend verifies a processed full refund against the captured payment before marking the order refunded or restoring stock. COD remittance and external courier settlement still require operational reconciliation. Test-mode and production credentials should be validated end to end before public launch.

Before exposing the store to customers, complete these acceptance checks on the deployed HTTPS site:

1. Rotate the JWT secret so any local or demo sessions expire; disable or reset old demo accounts. Confirm known demo passwords/codes cannot sign in, a real staff OTP arrives from the approved MSG91 template, resend/guess limits work, and password-reset email reaches an actual inbox.
2. Apply Alembic head to the production database, verify the startup migration and Redis checks, restore a PostgreSQL and product-media backup in a disposable environment, and confirm the release Flutter build calls the intended HTTPS API.
3. Exercise Razorpay test-mode success, failure, duplicate webhook, expired link, customer status check, cancellation, and processed refund. Then use live keys for one small real payment and refund and reconcile the dashboard with the order and bank settlement. Do not put live keys in the repository.
4. Verify each promised delivery pincode, fee, ETA, inventory quantity, actual courier/AWB workflow, and COD remittance. Keep automatic courier booking off until carrier credentials and a live booking/label/pickup test succeed.
5. Have the seller's accountant and food-compliance adviser approve invoicing, tax treatment, product claims, food-business registration, delivery and returns terms. The in-app order summary is intentionally not a tax invoice.
