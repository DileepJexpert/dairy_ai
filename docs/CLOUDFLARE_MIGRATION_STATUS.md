### Separate flow preview retired — 29 September 2026

The owner expected test orders in the existing Milterra site and asked to remove the extra preview if it consumed resources. Cloudflare's free D1 plan includes storage and a finite database count; the extra preview D1 occupied about 401,408 bytes and one database slot even when idle. The separate `milterra-flow-preview` Pages project, `milterra-api-flow-preview` Worker, and D1 `milterra-flow-preview` (`84e216c0-d5bc-4bab-a9cf-eba9e96bf20d`) were deleted. That D1 held only synthetic test records. The ignored local preview admin credential and Wrangler config were removed. Remote lists no longer show the preview Pages project or D1; querying the preview Worker deployments returns “Worker does not exist.” The existing `milterra-staging` Pages project (including `milterrafoods.com`), `milterra-api-staging` Worker, `milterra-staging` D1, school resources, and Katixo resources remain. After cleanup, the real domain and Worker `/ready` both returned HTTP 200. The real Worker still reports `test_mode=false`, and a simulator route returns HTTP 404.

**Same-site direction, not implemented yet:** To test the same customer/admin navigation without new Cloudflare resources, add an explicitly opted-in **test order** for a dedicated owner test account in the existing site. The server must authorize that choice, set `is_test_order` atomically at checkout, distinguish it in every admin/customer view, and permit simulated milestones or ledger entries only for that order and an authenticated admin. Ordinary COD orders must keep the real fulfillment and settlement paths. The current global `_test_commerce` and `_live_cod` modes are mutually exclusive, so do **not** turn on `TEST_COMMERCE_ENABLED` or `SIMULATION_ENABLED` globally in the real Worker as a shortcut. Tests also need to prove inventory, reporting, coupons, and refund records cannot mix test and real orders. Until this per-order design is implemented and verified, **the real site has no fake-shipping/refund test path**. Its COD checkout creates real orders.

### Security & Atomicity Resolution — 27 September 2026

Resolved critical P0 vulnerability and fulfillment race conditions across Cloudflare Worker backend and storefront:
1. **[P0] Token Disclosure Eliminated in Remote Environments**:
   - In [`customer_auth.py`](file:///c:/dileepkm/Learning/dairy_ai-with-backend/cloudflare/worker/src/customer_auth.py#L287-L340), `POST /api/v1/auth/forgot-password` now strictly fails closed with `503 Service Unavailable` whenever called on remotely accessible environments (`staging`, `production`, `development`) where external SMS/email gateways are not configured.
   - Disclosing reset tokens in response payloads is completely removed for all remote callers.
   - Automated testing harness allows token generation strictly in in-memory test runner (`ENVIRONMENT == 'test'` and `ALLOW_TEST_AUTH == True`).
   - Verified on live staging Worker: `POST /api/v1/auth/forgot-password` returns HTTP 503 and zero token metadata.
2. **[P1] Fulfillment State Machine & Event Insertion Atomicity**:
   - Replaced non-atomic batch updates with conditional `UPDATE ... RETURNING id, status` in [`commerce.py`](file:///c:/dileepkm/Learning/dairy_ai-with-backend/cloudflare/worker/src/commerce.py#L990-L1050).
   - If an order is concurrently cancelled while packing is submitted, the update matches 0 rows and returns `None`, raising `409 Conflict`. Crucially, no tracking event is inserted into `order_events`.
   - Updated `cancel_order` with conditional `UPDATE orders SET status = 'cancelled' WHERE id=? AND status IN ('placed', 'confirmed') RETURNING id, status`, preventing cancellation of already-packed or shipped orders.
3. **COD Settlement Concurrency Hardened**:
   - In [`commerce.py`](file:///c:/dileepkm/Learning/dairy_ai-with-backend/cloudflare/worker/src/commerce.py#L1060-L1095), `collect_cod_remittance` now uses atomic conditional SQL: `UPDATE orders SET payment_status='paid', remittance_reference=? WHERE id=? AND status='delivered' AND payment_status != 'paid' RETURNING id, payment_status, remittance_reference`.
   - Conflicting remittance references on already-settled orders raise `409 Conflict` and reject duplicate event insertions.
   - Exact-reference replay returns idempotent `200 OK` without creating duplicate timeline entries.
4. **Delivery Rates Transparency**:
   - Rates seeded in migration 0007 (Delhi ₹40, Noida ₹30, Gurugram ₹40, Lucknow ₹50, Mumbai ₹60, Bengaluru ₹60) are documented as staging operational defaults, not negotiated carrier contracts.
5. **Verification & Deployment**:
   - 37 backend tests in `cloudflare/worker/tests/` passed (100%), including race condition atomicity and staging 503 assertions.
   - Cloudflare Worker deployed to staging (`https://milterra-api-staging.todileepmaurya.workers.dev`, Version ID: `d62f508e-a560-4333-9c27-abfe0cc35c7f`).
   - Live endpoint check confirmed: `POST /auth/forgot-password` returns 503 Service Unavailable.
